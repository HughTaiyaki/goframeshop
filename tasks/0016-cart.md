# 任务 0016：购物车

状态：已完成。来源是原教程"购物车接口"一节。开发说明见 [`docs/development/goods-service.md`](../docs/development/goods-service.md#9-购物车) 和 [`docs/development/events.md`](../docs/development/events.md#53-下单成功orderplaced)。这是交易闭环的第二步：顾客把商品加进购物车，从购物车结算下单，下单成功后购物车里对应的商品自动移除。

## 新增了什么

| 类别 | 内容 |
| --- | --- |
| 建表 | `015_cart_and_order_placed.sql`：`goods.cart_item`（`(user_id, goods_id)` 唯一）；`orders.order_info.from_cart` |
| goods 服务 | 新增 `cart/v1.CartService`：`ListCartItems`、`AddCartItem`、`UpdateCartItem`、`DeleteCartItems`。只接受**商城用户**令牌，goods 因此新增 `jwtUser` 配置（用户公钥） |
| 前台 HTTP（需要登录） | `GET/POST/PUT/DELETE /frontend/cart`；下单接口多一个 `fromCart` |
| 事件 | 新增 `order.placed`：订单进入"待支付"（库存预留成功）时由 order 写入 outbox；goods 消费它，从下单用户的购物车里减去已购数量 |

## 规则

- **用户只能看到、修改、删除自己的购物车**：用户 ID 只来自令牌；每条 UPDATE、DELETE 语句都带 `user_id` 条件。别人的购物车项一律返回 NotFound。
- **加购**：同一商品再次加购时数量累加，不新增一行（`(user_id, goods_id)` 唯一键 + `INSERT ... ON DUPLICATE KEY UPDATE`，并发加购不会出现两行）。只能加购上架的商品。
- **上限**：每行数量 1–99（和下单的单行上限一致），累加后超过 99 返回 `FailedPrecondition`，不悄悄截断；每人最多 100 行。
- **列表**：按加入时间倒序；每一行带上商品当前的名称、价格、封面、可用库存，以及是否还能购买（下架或删除后为 false，但仍然显示，方便顾客删除）。价格是**当前价格**，不是加购时的价格：真正的价格以下单时服务端查询的为准。
- **下单后移除**：
  - 前端从购物车结算时，下单请求带 `fromCart: true`。
  - 订单库存预留成功（进入 `PENDING_PAYMENT`）时，order 在同一个事务里写入 `order.placed` 事件（用户、商品与数量、下单时间、是否来自购物车）。
  - goods 通过 Inbox 消费：只处理 `fromCart` 的订单；对每个商品，购物车数量减去购买数量，减到 0 就删除这一行。
  - **只动下单之前的购物车项**：如果顾客在下单之后又改过这一行（`updated_at` 晚于下单时间），说明这是新的意图，不动它。
  - 库存不足、下单失败的订单不会进入"待支付"，购物车保持原样。

## 与原教程的差异

| 原教程 | 本仓库 | 原因 |
| --- | --- | --- |
| `cart_info` 没有唯一键，重复加购新增一行 | `cart_item`，`(user_id, goods_id)` 唯一，数量累加 | 同一商品出现两行，前端很难处理；并发加购会产生重复行 |
| 删除只按 `id` | 删除、修改都带 `user_id` 条件 | 否则任何登录用户都能删别人的购物车 |
| 列表的 `Count()` 没有按用户过滤 | 总数按用户统计 | 原写法返回的是全站购物车总数 |
| `count` 不校验 | 1–99；累加超过上限时报错 | 防止 0、负数和超大数量 |
| 能加购任何商品 ID | 只能加购上架商品 | 不存在或下架的商品加进去也买不了 |
| 列表只有 `goods_id`、`count` | 带商品名、价格、封面、库存、是否可买 | 前端不用再逐个查商品详情 |
| `CartInfoCreateReq` 里有 `UserId`，网关从 ctx 取再塞进去 | 请求里没有用户 ID，goods 服务自己从令牌取 | 和其他服务一致：身份只来自验签过的令牌 |
| 网关取不到用户 ID 时 `panic` | 中间件已经拒绝未登录请求；后端再验一次 | `panic` 会被当成 500，而且是可以避免的 |
| 下单后删除购物车：原项目在"订单创建"消息里删除，消息在事务提交后用 goroutine 发出 | 预留成功时写进 outbox，由 Inbox 去重消费 | 事务提交后才发的消息会丢（详细设计 B1）；订单创建时就删，库存不足时购物车也没了 |
| `int` 的 ID | `BIGINT UNSIGNED` | 和其他表一致 |

## 顺手修复：多商品订单一直预留失败

端到端测试时发现，**任何包含两种以上商品的订单都会卡在 `RESERVING`**，直到预留超时关单。原因是 goods 的 `inventory.proto` 给 `repeated items` 写了 `v:required|length:1,50`，GoFrame 的 `length` 规则把列表当成它的 JSON 文本来量长度：两行商品的 JSON（`[{"goods_id":1,"quantity":1},{"goods_id":2,"quantity":1}]`）已经超过 50 个字符，于是 `ReserveInventory` 和 `ReleaseInventory` 都返回 `InvalidArgument`。订单服务把它当成"结果未知"不停重试，所以没有报错，只是一直不成功。只买一种商品时 JSON 不到 50 个字符，所以之前的测试都没有发现。

- 修复：规则改为 `v:required`；"最多 50 种"本来就由 goods 的逻辑层检查（`MaxInventoryItems`）。
- 回归测试 `app/goods/api/inventory_contract_test.go`：50 种商品的请求能通过生成的校验规则。改回旧规则时这个测试失败。
- 检查了所有 proto 和 HTTP 接口：没有别的列表字段用 `length`/`between`。这次新写的 `DELETE /frontend/cart` 本来也犯了同样的错，一并改掉。
- 已有数据卷里卡住的订单不用手动处理：重启 goods 后，订单服务的恢复任务会按原来的操作号继续预留或释放。
