# 任务 0013：RabbitMQ 与 Outbox / Inbox

状态：已完成。按[详细设计](../docs/GoFrame微服务商城详细设计.md) §7.3、§8 实现，开发说明见 [`docs/development/events.md`](../docs/development/events.md)。

原教程用 RabbitMQ 延迟消息做订单超时关单：下单事务提交后起一个 goroutine 发消息。任务 0011 解释过为什么当时没有照做（会丢消息，详细设计 B1）。这一轮把 RabbitMQ 引进来，用的是"消息先进数据库、再由投递器发出"的 Outbox 方式。

## 规则

```text
写事件：业务修改 + outbox_event（PENDING）    ← 同一个事务，要么都成功，要么都没有
投递：  Relay 领取一批（租约 15s）→ 发布 → 等 RabbitMQ 确认 → 标记 SENT
消费：  inbox_event（consumer, event_id）+ 业务修改  ← 同一个事务
        → 提交 → ACK
```

- **不会丢**：事件和业务数据一起提交。RabbitMQ 挂了，事件留在表里，恢复后补发。
- **可能重复，但只生效一次**：发布成功、还没来得及标记 SENT 时崩溃，会再发一次；消费方的 Inbox 记录了事件 ID，第二次只确认、不再执行。
- **发布要等确认**：只有收到 RabbitMQ 的 confirm，并且消息有队列接收（mandatory），才算发出。没有队列接收的消息会被退回，当作失败重试，不会悄悄丢掉。
- **事件是事实，不是命令**：订单服务收到到期消息后，仍然按数据库里的 `expires_at` 判断是否真的到期；提前到达的消息什么都不改。
- **乱序也不怕**：banner 记住每个手工位最后应用的版本号，旧版本的事件晚到也不会覆盖新的。
- **坏消息不卡队列**：格式错误、同一个事件 ID 内容却不同的消息，写进 `quarantine_event` 后确认，留给人工处理。
- **数据库扫描仍然保留**：延迟消息只是让关单更准时；消息丢了或晚了，恢复任务照样会关单。

## 与原教程的差异

| 原教程 | 本仓库 | 原因 |
| --- | --- | --- |
| 事务提交后起 goroutine 发消息 | 事件和业务数据在同一个事务里写进 `outbox_event`，由 Relay 投递 | 提交后、发送前崩溃会丢消息（B1） |
| 用请求的 ctx 发消息 | Relay 用自己的 ctx，与请求无关 | 请求结束后 ctx 被取消，发送会失败 |
| 不确认是否发成功 | publisher confirms + mandatory | 不知道 RabbitMQ 有没有收到 |
| 延迟交换机插件 | 普通持久队列 + 消息 TTL + 死信转发 | 插件的延迟消息只存在单个节点上 |
| worker 不消费任何消息 | 订单到期、商品变更两个真正的消费者，都有 Inbox 去重 | — |
| 只靠消息关单 | 消息负责准时，数据库扫描负责兜底 | 消息系统不是唯一的记录 |

## 范围外

- 订单的其他事件（已支付、已关闭）：目前没有消费者，发出去没有队列接收会被当作失败，所以先不发。
- 消费失败的持久重试表（详细设计 §8.2 的 retry_task）：目前消费失败就不确认，让 RabbitMQ 重投（间隔 1 秒）。两个消费者的业务步骤都只是本地数据库操作，失败只可能是数据库不可用。
- 事件表的清理（保留期）。
- search 服务改为消费 `goods.changed`：它现在用 binlog，同样可靠，暂不改。
- ~~链路追踪的 `traceparent`~~：已在[任务 0014](0014-tracing.md) 加上。

## 验收标准

- 单元测试（`-race`）：订单进入"待支付"时恰好写一条事件，送达时间是 `expiresAt + 1s`；`Settle` 对未到期的订单不做任何事，对到期的订单关单并释放库存。
- 集成测试（`GOFRAMESHOP_IT=1`，真实 MySQL 和 RabbitMQ）：
  - 发布者：收到确认才返回；没有队列接收时返回"不可路由"，通道仍然可用；带 TTL 的消息到期后转到死信路由键，而且不会提前送达。
  - Relay：事务回滚不留事件；两个 Relay 同时投递 60 条，每条恰好发一次，全部标记 SENT；发不出去的事件保持 PENDING，记下重试时间，未到时间不重试。
  - Inbox：同一事件处理 3 次只执行 1 次；内容不同、格式错误的进隔离表；业务步骤失败时连同 Inbox 记录一起回滚，重投后能执行；10 个并发副本只执行 1 次。
  - 订单到期消费者：到期订单在 Inbox 事务里关单，重投不重复；提前到达的消息不改订单。
  - banner 消费者：版本 20 先到、版本 10 后到，结果是版本 20；下架后前台列表不显示，重新上架后恢复；删除后隐藏；重投不重复执行。
  - goods：改上下架、改名、删除各写一条事件，内容正确，id 递增。
- 本地端到端（10 个进程 + RabbitMQ）：
  - 把恢复任务间隔调到 60 秒，订单在第 31 秒被延迟消息关单（日志 `closing (expiry message)`）。
  - 停掉 RabbitMQ 时照常下单，事件留在 outbox 并按退避重试；RabbitMQ 恢复后补发，两个消费者自动重连，订单照样被消息关单。
  - 后台改商品名、下架、上架、改回原名，前台手工位依次显示新名字、消失、出现、恢复原名。
  - 支付端到端 27 项仍然全部通过。日志里没有令牌和密码。
- `go test ./...`、`go vet ./...`、`go mod verify`、`docker compose config` 通过；重新生成代码没有差异（事件表不生成 DAO）；GoFrame 仍为 v2.10.2。
