# 任务 0015：前台接口补齐与热门推荐

状态：已完成。来源是原教程"对接前端-接口调整"和"热门推荐-接口调整"两节。这是交易闭环的第一步：顾客能在前台改资料、改密码，首页能展示运营挑选的热门商品。后面依次是购物车（0016）、发货与收货（0017）、售后审批与退款（0018）。

## 新增了什么

| 类别 | 内容 |
| --- | --- |
| user 服务 | 新增 `UpdateProfile` RPC：整体替换头像、性别、签名；用户名和状态不能改 |
| 前台 HTTP（需要登录） | `PUT /frontend/user/password`（修改密码，要当前密码）、`PUT /frontend/user/profile`（修改资料，返回新资料） |
| 建表 | `014_goods_hot_sort.sql`：`goods_info.sort`（`SMALLINT UNSIGNED`，默认 0）和索引 `idx_goods_hot (status, sort)`，可以重复执行 |
| goods 服务 | `GoodsInput.sort`（0–9999）；`ListGoodsRequest.hot_only`；`GoodsSummary.sort`、`Goods.sort` |
| 前台 HTTP（公开） | `GET /frontend/goods?isHot=1`：只返回热门商品，按推荐权重从高到低 |
| 后台 HTTP | 创建、修改商品可以填 `sort`；列表多了 `isHot` 筛选；列表和详情返回 `sort` |
| 缓存 | 商品详情缓存键从 `goods:v1:detail:` 升到 `goods:v2:detail:`（缓存内容多了 `sort`），旧键在 TTL 内自然过期 |

`sort` 的含义：**0 表示不是热门；大于 0 进入热门列表，数值越大越靠前**，权重相同时新商品在前。它和 `goods_images.sort`（图片顺序，小的在前）没有关系。

## 与原教程的差异

| 原教程 | 本仓库 | 原因 |
| --- | --- | --- |
| 改密码、改资料直接调用 | 改密码要先验证当前密码；新密码 8–128 位 | 只拿到令牌（比如被盗）不能把真正的主人锁在外面 |
| 头像随便填 | 只接受空值或 `http`/`https` 绝对地址，不能带账号密码或控制字符；注册时也按同样规则检查 | 头像会被放进 `<img>`，也可能被前端做成链接。`javascript:`、`data:` 地址不能进库 |
| 性别、签名不校验 | 性别只能是 0、1、2；签名最多 255 个字符，前后空格去掉 | 与列定义一致，超长时返回参数错误而不是数据库错误 |
| `sort TINYINT`（有符号，-128～127） | `SMALLINT UNSIGNED`，接口限制 0–9999 | 负数没有意义；127 档不够运营拉开差距 |
| 查询条件 `uint32 is_hot` | gRPC 用 `bool hot_only`；HTTP 仍是 `isHot`（0 或 1，其他值返回参数错误） | gRPC 内部用 bool 更清楚；HTTP 保持教程的参数名，方便前端对接 |
| 加了 `is_hot` 后所有列表按 `sort` 倒序 | 只有 `isHot=1` 时按 `sort` 倒序；普通列表仍然新的在前 | 普通列表突然改变顺序会让前端分页错乱，而且大部分商品 `sort` 都是 0 |
| 按 `sort` 倒序 | `sort` 倒序，相同时按 ID 倒序 | 只按 `sort` 排序时，权重相同的商品在翻页时可能重复或漏掉 |
| 前台返回 `sort` | 前台不返回 `sort`，只用 `isHot` 筛选；后台返回 | 推荐权重是运营数据，前台只需要知道"这是热门" |

## 设计说明

**为什么 `sort` 放在 `GoodsInput` 里，而不是像上下架那样单独一个接口？** 教程把它当成商品的普通字段，后台表单一起提交。代价是：修改商品是整体替换，**不填 `sort` 就等于 0**，商品会退出热门列表。后台网关的字段说明写明了这一点。以后如果运营要频繁调整热门（比如拖拽排序），再加一个只改 `sort` 的接口。

**为什么改 `sort` 也会发 `goods.changed` 事件？** 修改商品走的是同一个事务（任务 0013），事件描述的是商品的当前状态。banner 收到后核对名称和上下架状态，`sort` 变了它什么都不做。这是正确的：事件是事实，消费方按自己的需要处理。

**search 服务要不要改？** 按 `AGENTS.md` 检查了 `app/search/internal/source/mysql.go` 的 `docQuery` 和 `idColumns`：`docQuery` 按列名查询，新增列不影响；搜索按相关度、销量、价格排序，不需要推荐权重。所以 search 不改。改 `sort` 会产生一次 binlog，search 会重建这件商品的文档，结果不变。

**缓存为什么要升版本？** 缓存里的商品是 JSON。不升版本时，旧缓存里没有 `sort`，解码出来是 0，在 TTL（1 小时）内后台看到的权重是错的。升到 `v2` 后旧键没人读，到期自动删除。

## 范围外

- 刷新令牌和吊销：改密码后，已经签发的令牌在过期前（默认 2 小时）仍然有效。这是任务 0004 就记录的已知限制。
- 改用户名、绑定手机、找回密码。
- 热门商品的缓存：列表本来就不缓存（组合太多），热门列表也一样。
