# 任务 0021：故障实验

状态：已完成。开发说明见 [`docs/development/fault-experiments.md`](../docs/development/fault-experiments.md)。按[详细设计](../docs/GoFrame微服务商城详细设计.md) §8.4、§10 实现。把 T1–T10 做成**可以重复执行**的实验：启动真实进程，在精确的位置注入故障（进程崩溃、响应丢失、消息丢失、并发竞争），恢复后检查不变量，输出报告。这是交易闭环和可观测性之后的验证环节，也为日志诊断 Agent 提供"真实发生过什么"的标准答案。

## 和已有测试的区别

已有的 `GOFRAMESHOP_IT=1` 集成测试在**仓库层**验证单个机制：库存账本的并发、付款与关单的行锁、Inbox 去重。它们没有真实的进程、网络和崩溃。故障实验在**系统层**验证：

- 服务以独立进程运行（user、goods、order、paysim），通过 gRPC 和 RabbitMQ 通信，和平时一样；
- 故障发生在真实的窗口里：比如订单已经写入数据库、还没调用库存时，order 进程直接退出；
- 恢复靠系统自己（重启、恢复任务、重投），实验只检查最后的状态对不对。

设计 §2.2 的 B1–B7 是原教程代码里的问题，本仓库已经重写了对应的部分，所以没有"旧链路"可以复现；这些窗口由下面的 T 实验在新实现上验证。

## 怎么注入故障：failpoint

新增 `utility/failpoint`：代码里放几个命名的注入点，**只在环境变量 `GOFRAMESHOP_FAILPOINTS` 列出时生效**，否则只是一次布尔判断。

| 动作 | 效果 | 用途 |
| --- | --- | --- |
| `exit` | 立刻结束进程（`os.Exit`，不跑 defer），等同于崩溃 | 在两步之间崩溃 |
| `error` | 让这一步返回错误：事情做了，但调用方收不到结果 | 响应丢失 |
| `pause` | 停在这里，等实验放行（用目录里的标记文件通信） | 用屏障控制两个动作的先后，不靠 `sleep` |

| 注入点 | 位置 | 窗口（设计 §8.4） |
| --- | --- | --- |
| `order.create.after-insert` | 订单写入后、调用库存预留前 | 下单持久后 Reserve 前 |
| `goods.reserve.after-commit` | 库存预留事务提交后、返回响应前 | Reserve 成功响应丢失 |
| `order.payment.before-record` | 确认付款、锁订单行之前 | 付款与关单竞争 |
| `eventbus.relay.after-publish` | 事件已被 RabbitMQ 确认、标记 SENT 前 | 发布成功但 SENT 未更新 |
| `eventbus.inbox.after-commit` | 消费事务已提交、ACK 前 | 消费提交后 ACK 前 |

生产配置里没有这个环境变量，注入点永远不会生效。

## 实验（设计 §10）

| ID | 注入与操作 | 判定 |
| --- | --- | --- |
| T1 | 库存 10，100 个不同的下单请求同时购买 1 件 | 成功预留的订单 ≤ 10；可用、预留、已售都不为负，三者之和不变 |
| T2 | 同一个 `requestId` 并发 20 次；再用同一个 `requestId` 换参数 | 只有一个订单；换参数返回冲突 |
| T3 | `goods.reserve.after-commit=error`：预留已提交，响应丢失 | 订单先停在预留中，恢复任务用同一个操作号重试，只有一份预留，最后进入待支付 |
| T4 | 直接调库存接口：先释放、后预留同一个订单 | 迟到的预留被拒绝（墓碑），库存不变 |
| T5 | `order.payment.before-record=pause`：付款回调停在锁订单之前，此时顾客取消订单，再放行 | 订单最终关闭且付款被退回（或者付款先到时为已支付）；已售的库存不会被释放，退款只有一次 |
| T6 | 已支付的订单再收到一条到期消息 | 订单仍是已支付，不产生释放库存的操作 |
| T7 | `eventbus.inbox.after-commit=exit`：购物车消费者提交后、ACK 前崩溃，重启 | RabbitMQ 重投，Inbox 去重：购物车只减一次，日志出现 `message.redelivered` |
| T8 | `eventbus.relay.after-publish=exit`：order 发出事件后、标记 SENT 前崩溃，重启 | 同一个 `event_id` 重发，消费方只处理一次 |
| T9 | 到期消息丢失（清空延迟队列） | 数据库扫描在到期后关单并释放库存，不会永远待支付 |
| T10 | 新旧 Protobuf 对照 | 已有字段的编号、类型、名字都没变；删掉的字段编号保留，不能复用 |

另有一个**崩溃恢复**实验 `C1`：`order.create.after-insert=exit`，订单写入后 order 进程立即崩溃；重启后恢复任务接着预留，订单进入待支付，库存只预留一次。

## 不变量（每个实验结束后都检查）

- 库存：`available`、`reserved`、`sold` 都不为负；`available + reserved + sold` 等于实验开始时的总量。
- 预留与订单一致：待支付、付款确认中的订单有 RESERVED 的预留；已支付的是 COMMITTED；已关闭的没有 RESERVED。
- 已支付的订单，库存提交恰好一次；任何订单的技术退款不超过一次。
- 没有停在中间状态（预留中、关闭中、付款确认中）超过恢复期限的订单。

## 怎么跑

```bash
make infra-up
make fault-trade          # 全部实验，约 N 分钟；报告写到 reports/fault/
```

- 实验程序自己构建并启动 user、goods、order、paysim，使用你本地配置的**实验副本**（缩短支付超时和恢复间隔，`environment=experiment`），结束后全部停掉，不改你的配置。
- 每个实验用自己新建的商品和用户，互不干扰，也不影响已有数据。
- 端口被占用（本地正在跑这些服务）时直接退出并提示。

报告（`reports/fault/<时间>.md` 和 `.json`）：每个实验的结果、耗时、注入的故障、恢复用了多久、相关的订单号和链路 ID。报告只给人看；按设计 §9.3，故障的名字不会写进日志、指标或链路。

## 范围外

- 压测（`make bench-trade`）。
- 网络层故障（丢包、延迟）：用 `error` 和 `pause` 在应用层模拟。
- 节点级故障：单机 Compose 不代表高可用（设计 §1）。

## 实验发现并修复的问题

两个问题都是以前的任务留下的，单元测试和集成测试都没有发现，而是被系统层的实验找出来的：

### 1. 下单后购物车被整行删掉（任务 0016）

**T7 发现。** 购物车里有 2 件，从购物车下单买 1 件，购物车应该剩 1 件，实际整行没了。

原因：`order.placed` 的消费者对每件商品执行两条语句：先"数量大于已购的减去已购数量"，再"数量不大于已购的删除"。2 件减 1 件剩 1 件，第二条语句一看 1 ≤ 1，又把这一行删了。只要剩下的数量不超过买走的数量，就会出错。0016 的集成测试恰好用了"3 件买 1 件"（剩 2 件，大于 1），没有覆盖到。

修复：先删除、再减数量，这样每一行只会匹配其中一条语句。`cart_integration_test.go` 加了"2 件买 1 件剩 1 件"，修复前这个用例失败。

### 2. 重新投递的事件被当成冲突隔离（任务 0013）

**T8 发现。** 投递器把事件发给 RabbitMQ 后、标记 SENT 前崩溃，重启后重发同一个事件。消费方没有把它当成重复事件确认，而是放进了 `quarantine_event`（"event id reused with a different payload"），并记一条 ERROR 日志。业务修改仍然只发生了一次，但设计 §8.4 规定的"重发同一个 event_id，Inbox 去重"没有做到，而且会给日后的诊断留下一条误导性的错误记录。

原因：Inbox 用**整个消息体**的哈希判断"是同一个事件"还是"同一个 ID 换了内容"。消息体里有 `traceparent`，也就是**这一次发送**的链路上下文：每次发送都是新的 span，内容不一样，哈希就不一样。

修复：指纹只覆盖决定事件是什么的部分，也就是类型、聚合 ID、版本和 payload，不包括链路上下文这类传输信息。已有的 Inbox 记录存的是旧的整体哈希，比较时两种都认，升级期间正在途中的事件不会被误判。`eventbus_integration_test.go` 加了"同一个事件带不同的 traceparent 再来一次"，修复前这个用例失败。T8 还会检查实验中的事件都没有被隔离。

### 实验本身的问题

第一轮有 4 个实验因为实验程序的问题失败：等待进程退出时读走了"已退出"的通知，后面的重启一直等不到。改成关闭通道后解决。这不是商城的问题。
