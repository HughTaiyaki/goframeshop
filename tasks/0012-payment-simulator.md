# 任务 0012：支付模拟器与订单支付

状态：已完成。按[详细设计](../docs/GoFrame微服务商城详细设计.md) 6.1、6.4 节实现，开发说明见 [`docs/development/payment.md`](../docs/development/payment.md)。

原教程没有支付章节（订单只有一个 `pay_type` 字段，状态由数字直接改）。这一轮补上"付款"这一环，并把订单从"待支付"推进到"已支付"。

## 新增了什么

| 类别 | 内容 |
| --- | --- |
| 进程 | `app/paysim` 支付模拟器：gRPC `:31009`（商户接口，只给订单服务用），HTTP `:8399`（付款人的收银台页面） |
| 建库建表 | `010_payment_simulator_schema.sql`：模拟器自己的库 `paysim`（`payment`、`refund`）<br>`011_order_payment_schema.sql`：`orders` 库新增 `payment`、`tech_refund`，`order_info` 新增 `paid_at` |
| 订单状态 | 新增 `PAYMENT_CONFIRMING`（已付款，正在提交库存）、`PAID`、`EXCEPTION`（已付款但库存提交不了，自动退款） |
| gRPC | 订单服务新增 `PaymentService`：`PayOrder`（顾客）、`NotifyPayment`（公开，靠签名）<br>模拟器 `PaymentProvider`：`CreatePayment`、`ClosePayment`、`QueryPayment`、`RefundPayment` |
| 前台 HTTP | `POST /frontend/order/pay`：返回收银台地址；已付款时直接确认<br>`POST /frontend/payment/notify`：模拟器的回调入口，不需要登录 |
| 后台任务 | 订单恢复任务新增：提交库存、关单前先关闭支付单、重试技术退款<br>模拟器新增：回调重试（2s、4s、8s……，最多 10 次） |
| 身份 | 第四对密钥：模拟器用私钥给回调签名，订单服务用公钥验签。模拟器的商户接口只认订单服务的服务令牌 |
| 共享代码 | `utility/paysign.go`：回调签名与验签、回调内容 `PaymentNotice` |
| 售后 | 订单能走到 `PAID` 了，售后申请（任务 0010）现在可以用了 |

## 规则

```text
顾客 ──去支付──▶ 订单服务 ──创建支付单──▶ 模拟器 ──返回收银台地址──▶ 顾客付款
模拟器 ──签名回调──▶ gateway-h5 ──▶ 订单服务 ──查询支付单──▶ 模拟器
                                      └─ 确认 ─▶ PAYMENT_CONFIRMING ─提交库存─▶ PAID
```

- **支付单号由订单号决定**：`P` + 订单号。重复点击、后台任务、回调说的都是同一张支付单。
- **付款和关单只有一个能成功**：模拟器在同一行、同一个事务里裁定。关单先到时会留下"已关闭"墓碑，之后的创建和付款都会被拒绝。
- **回调只是提示**：签名通过后，订单服务会去模拟器**查询**真实结果，并核对订单号、金额和币种，然后才记账。伪造的、5 分钟以前的回调都会被拒绝。
- **记账和改订单在一个事务里**：订单行加锁后再判断。订单还在等付款，就进入 `PAYMENT_CONFIRMING`；订单已经在关闭，就保持关闭，并安排一笔技术退款。
- **关单先关支付单，再还库存**：模拟器联系不上时，订单停在 `CLOSING`，库存先不还。模拟器说"已经付了"，就先记账、安排退款，然后照常还库存。
- **退款最多一次**：每笔支付最多一笔技术退款，退款单号固定为 `TR` + 支付单号，模拟器按退款单号去重。
- **回调丢了也不怕**：顾客再点一次"去支付"，订单服务会发现模拟器那边已经付款，当场确认。

## 与原教程的差异

| 原教程 | 本仓库 | 原因 |
| --- | --- | --- |
| 没有支付，状态由接口直接改成"已支付" | 独立的支付模拟器进程和库，订单服务只能通过它的接口打交道 | 真实的支付渠道是外部系统：会超时、会重复回调、回调会丢 |
| — | 回调带签名，并且只当提示，结果以查询为准 | 回调地址是公开的，任何人都能往里发请求 |
| — | 付款和超时关单可能同时发生，用行锁裁定，晚到的付款自动退款 | 不处理的话，会出现"钱收了，订单却关了"或者"库存卖了两次" |
| — | 库存在付款后才从"预留"变成"已售" | 详细设计 6.3：未付款的订单不应该真正卖掉库存 |

## 范围外

- 售后的审批（同意、拒绝）和按商品部分退款：模拟器目前只支持整单退款，技术退款够用；售后退款下一步做。
- 发货（`SHIPPED`）、完成（`COMPLETED`）。
- 回调和关单事件改走 RabbitMQ + Outbox/Inbox：下一轮。
- ~~后台任务每一轮用同一个链路 ID 记日志~~：已在[任务 0014](0014-tracing.md) 解决。
- 付款人身份：模拟器没有付款人账号，拿到收银台地址的人都能付款（只是演示）。

## 验收标准

- 单元测试（`-race`）：
  - 模拟器：创建幂等、关单墓碑、付款与关单互斥（200 次并发）、过期不能付款、重复付款只扣一次、退款只退一次、回调签名、重试和放弃。
  - 订单：付款 → 回调 → 提交库存 → `PAID`；伪造和过期的回调被拒；回调说已付但查询说未付时不动；回调丢失后再点"去支付"能恢复；提交库存没有结果时由后台任务重试；关单时模拟器联系不上就不还库存；取消订单会在模拟器留下墓碑；取消与付款同时发生时退款一次；库存提交被拒时进入 `EXCEPTION`，退款后关单；金额对不上不记账；不能替别人付款；付款与超时关单并发 100 次，结果只有"已支付、没有退款"或"已关闭、付了钱就退一次"两种。
  - 鉴权：`PayOrder` 只接受用户令牌，`NotifyPayment` 不需要令牌。
- 集成测试（`GOFRAMESHOP_IT=1`，真实 MySQL）：
  - 模拟器：付款与关单并发 30 轮；20 个并发的首次请求只插入一行；10 个并发退款只退一次。
  - 订单：记账与关单并发 30 轮，结果和"谁先拿到行锁"一致；重复记账不重复安排退款；`EXCEPTION` 退款后进入 `CLOSING`；已退款的支付不会被改回成功。
- 本地端到端（9 个进程，27 项检查全部通过）：正常付款、回调丢失后恢复、取消与付款同时发生时自动退款、替别人付款返回 `code:5`、伪造回调返回 `code:16`、超时关单后模拟器支付单关闭且付款返回 409；停掉 gateway-h5 后模拟器按 2s、4s、8s 重试，重启后第 4 次送达。日志里没有令牌、密钥和密码。
- `go test ./...`、`go vet ./...`、`go mod verify`、`go mod tidy` 无变化、`docker compose config` 通过；重新生成代码没有差异；GoFrame 仍为 v2.10.2。
