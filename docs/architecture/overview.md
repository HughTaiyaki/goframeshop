# 架构概览

## 目标

构建一个规模可控的商城系统：它既能作为后端项目作品，也能作为日志诊断 Agent 的受控实验环境。

## 实现顺序

1. 使用本地 MySQL 和 etcd，并提供可复现的数据库初始化。
2. 创建用户服务脚手架并定义稳定的 Protobuf 协议。
3. 实现最小结算链路：网关、订单、库存和支付模拟器。
4. 加入结构化日志、指标、链路追踪和关联标识。
5. 加入具有已知标准答案的确定性故障注入。
6. 实现只读日志诊断 Agent、工具审计日志和评测数据集。
7. 商品目录和结算链路可信后，再选择性实现导购 Agent。

## 服务边界

- `gateway`：外部 HTTP 边界。用公钥验签并早拒绝，再把令牌原样转发给后端。
- `user`：用户资料和收货地址，不持有支付凭据；唯一持有 JWT 私钥、能签发令牌的服务。
- `interaction`：点赞、收藏、评论。只持有 JWT 公钥。按原教程顺序先于结算链路实现，它不改变下面的实现顺序。
- `admin`：后台管理员身份，持有**另一对**密钥，与商城用户身份完全分开。
- `file`：文件元数据。文件内容在对象存储里，其他服务通过 `file_id` 引用文件。需要快速读取的服务（goods）在引用时复制一份 URL，file 服务仍是文件的权威来源。
- `goods`：商品、商品图片、三级分类、上下架，以及库存账本（预留、提交、释放，见详细设计 ADR-M2 和 §6.3）。读公开并带缓存，写只接受管理员令牌。
- `order`：订单生命周期（详细设计 §6.1）。下单时预留库存，取消或超时后释放；后台任务负责推进卡住和过期的订单。它有自己的服务身份（第三对密钥），只能用来调用 goods 的库存接口和支付模拟器的商户接口。支付流程（去支付、验签回调、提交库存、晚到付款的技术退款）也在这里（`logic/order/paymentflow.go`）。
- `banner`：首页轮播图和手工位。图片按 `file_id` 引用，商品名在保存时从 goods 复制，之后由 goods 的 `goods.changed` 事件保持同步。
- `search`：商品搜索。Elasticsearch 索引是 goods 数据的只读投影，通过 binlog 跟随变化，可以随时重建；它直接读取 goods 的表（只读账号），这是有意接受的耦合。
- `gateway-admin`：后台 HTTP 边界，负责把校验过的图片写入对象存储；与 `gateway-h5` 一样不持有数据库。
- `order`：订单生命周期和幂等边界。
- `inventory`：库存预留与释放状态机。
- `paysim`（payment-simulator）：独立进程和独立的库，代表外部支付渠道（ADR-M1），为开发和评测提供确定性的支付结果，也能制造故障（回调丢失、回调失败重试）。订单服务只能通过它的接口打交道。
- `incident-agent`：读取遥测数据并输出有证据支撑的诊断。

本学习环境使用 etcd 进行服务发现，不把它当作业务数据存储。MySQL 保存持久化商城状态，是唯一的权威数据源。Elasticsearch 同样只是投影，不是数据源。Redis 目前只给 goods 服务做读缓存，不持久化，任何时候清空都不会丢数据；服务在 Redis 不可用时回退到 MySQL。以后 Redis 还可以保存短期 Agent 会话、限流状态等可以丢失的数据，但不能用它决定库存。

链路追踪（[`development/tracing.md`](../development/tracing.md)）：每个进程把 span 经 OTLP 发给 OpenTelemetry Collector，再转给 Jaeger；服务不直接依赖追踪后端。上下文按 W3C 规范在 HTTP、gRPC 和 RabbitMQ 消息头里传播；很久之后才发生的异步工作（订单到期）另起链路并用 Span Link 关联。敏感内容在进程内和 Collector 各脱敏一次。

RabbitMQ 只负责**投递**服务之间的事件，不是任何事实的唯一记录：事件先和业务修改在同一个事务里写进发布方自己库里的 `outbox_event`，再由投递器发出；消费方在自己的库里用 `inbox_event` 去重（详细设计 §8，[`development/events.md`](../development/events.md)）。所有路由写在 `utility/rabbitmq/topology.go`。现在的两条：order 发给自己的延迟到期事件（准时关单，数据库扫描兜底），goods 发给 banner 的商品变更事件。

## Agent 边界

第一个 Agent 只能使用只读工具查询日志、链路、指标和部署元数据。它必须区分事实证据与推断，引用遥测标识；证据不足时不能声称已经确定根因。

支付写操作和基础设施变更需要单独设计审批机制，不属于初始 Agent Harness 的范围。
