# 01 · 一次请求的完整旅程

> 用一条真实的请求把整条链路串起来：**新建一个收货地址**。
> 读完后你应该能在脑子里画出这条线，并指出每一跳对应的文件。

## 全局链路

```
浏览器
  │  POST /frontend/consignee
  │  Content-Type: application/json
  │  Authorization: Bearer eyJhbGciOi...   ← 登录时拿到的令牌
  ▼
┌───────────────── gateway-h5 (:8199) ─────────────────┐
│ 1. MiddlewareCORS            允许跨域，挡掉 OPTIONS    │
│ 2. 路由 /frontend → controller                        │
│ 3. 参数绑定 + v: 标签校验    名字为空直接 400          │
│ 4. MiddlewareAuth            用公钥验签，不过就拒绝   │
│ 5. HTTP 结构体 → gRPC 结构体                          │
│ 6. 用 etcd 把 "user" 解析成真实地址                   │
│    GrpcClientForwardAuth     令牌原样带进 gRPC 调用   │
└──────────────────────┬───────────────────────────────┘
                       │ gRPC  CreateConsignee
                       ▼
┌───────────────── user (:31001) ──────────────────────┐
│ 7. safeUnaryLog         只记方法名/状态码/耗时        │
│ 8. UnaryServerAuth      再验一次，得出"这是用户 42"   │
│    UnaryValidate        按 .proto 里的 v: 标签再校验  │
│ 9. Controller           取身份 → 调 service           │
│ 10. logic               业务规则（默认地址互斥）      │
│ 11. repository          SQL 语义                      │
│ 12. DAO                 生成的表/字段常量             │
└──────────────────────┬───────────────────────────────┘
                       │ INSERT INTO consignee_info
                       ▼
                    MySQL 8.4.11
```

## 逐跳对应到文件

| 跳 | 文件 | 它在做什么 |
| --- | --- | --- |
| 1 | `utility/http.go` → `MiddlewareCORS` | 浏览器跨域预检 |
| 2 | `app/gateway-h5/internal/cmd/cmd.go` | `group.Bind(user.NewV1(), interaction.NewV1())` 自动注册路由 |
| 3 | `app/gateway-h5/api/user/v1/consignee.go` | 请求结构 + `v:"required"` 校验规则 |
| 4 | `utility/http.go` → `MiddlewareAuth`；白名单在 `app/gateway-h5/internal/cmd/cmd.go` 的 `publicRoutes` | 用公钥验签，默认拒绝 |
| 5 | `app/gateway-h5/internal/controller/user/user_v1_consignee_create.go` | 手工字段映射 |
| 6 | `utility/grpc.go` → `RegisterEtcdResolver`；`utility/auth.go` → `GrpcClientForwardAuth` | 服务名 → IP:端口；令牌放进 gRPC metadata |
| 7 | `utility/grpc.go` → `UnarySafeLog`（由 `NewGrpcServerConfig` 装配） | 关掉会打印密码的默认日志 |
| 8 | `utility/auth.go` → `UnaryServerAuth`；校验规则来自 `.proto` 里的 `// v:required|length:1,64` 注释 | 先鉴权再校验，未登录的调用方看不到校验规则 |
| 9 | `app/user/internal/controller/consignee/consignee.go` | 薄薄一层 |
| 10 | `app/user/internal/logic/consignee/consignee.go` | 业务规则 |
| 11 | `app/user/internal/repository/consignee.go` | `WhereNull(deleted_at)`、事务 |
| 12 | `app/user/internal/dao/internal/consignee_info.go` | **生成代码，不要手改** |

## 三个容易卡住的点

### 1. 为什么有 etcd？不能写死地址吗？

可以，但你会立刻遇到两个问题：

- user 服务换了端口，网关要改代码重新发布；
- user 服务起了 3 个副本，网关该连哪个？

etcd 是一个"电话簿"：服务启动时把自己的地址写进去（`grpc.name: "user"`），调用方按名字查，拿到当前活着的全部地址，gRPC 自己做负载均衡。

```
user 服务启动  ──写入──▶  etcd:  /service/user → 127.0.0.1:31001
gateway 调用   ──查询──▶  etcd:  /service/user → [127.0.0.1:31001]
```

**etcd 只存"谁在哪"，不存业务数据。** 用户、地址永远在 MySQL。

### 2. 为什么要校验两次？

- **第 3 步（网关）** 是为了让错误请求不要浪费一次网络往返 —— 名字为空还发 RPC 是纯粹浪费。
- **第 7 步（user 服务）** 是因为微服务不能假设调用方是好人。user 服务可能被 job、被测试、被别的服务调用。协议层的校验是它自己的防线。

这跟单体里"前端校验了后端还要校验"是同一个道理，只是中间隔了一个网络。

### 3. 令牌是谁签发、谁验证的？

令牌用 **Ed25519** 签名。这是一种非对称算法，私钥和公钥分开：

```
user         持有私钥  → 能签发，也能验证
gateway-h5   持有公钥  → 只能验证
interaction  持有公钥  → 只能验证
```

```
登录：  浏览器 ──用户名+密码──▶ 网关 ──Login──▶ user  用私钥签发（sub=42，2 小时过期）
之后：  浏览器 ──Bearer <令牌>──▶ 网关 公钥验签 ──authorization metadata──▶ 后端服务 公钥再验一次
```

为什么不用一个共享密钥（HS256）？HS256 是对称算法：能验签的一方也能签发。三个进程都持有密钥，就有三个地方能伪造任何人的令牌。用 Ed25519 后，公钥就算泄露，也伪造不出令牌。

为什么网关验过了，后端还要再验一次？因为后端可能被网关以外的调用方直接访问，比如别的服务、脚本或测试。每个服务都应该自己确认"你是谁"，而不是相信上游说的话。

网关这一层的作用是**早拒绝**：没有有效令牌的请求，根本不会产生一次 gRPC 调用。

网关和每个服务都是**默认拒绝**的：只有白名单里的接口不需要登录（注册、登录、看评论），其他都要令牌。新加的接口忘了配置时，结果是"拒绝"，不会是"裸奔"。

以前这里用的是一个明文的 `X-User-Id` 头，网关说你是谁你就是谁。这个机制已经删除。现在单独发 `X-User-Id` 或 `x-user-id` 都会被拒绝，有测试专门覆盖这一点。

### 4. 不是用户发起的请求：支付回调

上面的请求都是浏览器发起、带着用户令牌的。支付成功后，**支付模拟器**会主动发一个请求过来，告诉商城"这笔钱付了"：

```
paysim ──POST /frontend/payment/notify（请求体 + X-Paysim-Signature）──▶ gateway-h5 ──NotifyPayment──▶ order
                                                                               │
paysim ◀────────────────────────── QueryPayment（"这笔到底付了没有？"）─────────┘
```

它没有用户令牌，所以这个路由在白名单里。那靠什么防止别人伪造"支付成功"？两道关：

1. **签名**：模拟器用自己的私钥（第四对密钥）签名请求体，订单服务用公钥验签。网关原样转发请求体，一个字节都不改，否则签名就对不上了。
2. **只当提示**：就算签名对了，订单服务也不相信请求体里写的"成功"，而是回头去**查询**模拟器，以查询结果为准，再核对金额和订单号。

这和前面"每个服务都自己确认你是谁"是同一个思路：别人说的话只是线索，事实要自己去核实。完整过程见 [`development/payment.md`](../development/payment.md)。


### 5. 亲眼看到这趟旅程：链路追踪

上面的旅程不用靠想象。每个服务都会把自己做的每一步（收到的 HTTP 请求、发出和收到的 gRPC 调用、每条 SQL）报告给 Jaeger，并且用同一个 **trace id** 串起来：调用下游时，trace id 跟着请求头（HTTP）或 metadata（gRPC）一起传过去。

打开 <http://127.0.0.1:16686>，Service 选 `gateway-h5`，找一次 `/frontend/order`，能看到网关 → 订单 → 商品、用户这棵树，以及每一步的耗时。日志里每行开头 `{...}` 的那串十六进制就是 trace id，可以直接在 Jaeger 里搜。

令牌会跟着请求一路传，所以追踪数据在离开每个进程前都会去掉令牌、带值的 SQL 这类敏感内容。详见 [`development/tracing.md`](../development/tracing.md)。
