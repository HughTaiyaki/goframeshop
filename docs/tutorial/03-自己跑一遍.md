# 03 · 自己跑一遍

> 从零到"地址列表返回一条数据"。所有命令都在 `goframeshop/` 下执行。

## 第 0 步：确认工具

```bash
make env-check
```

需要 Go ≥ 1.24.5、`gf`、Docker Desktop 处于运行状态。

## 第 1 步：起基础设施

```bash
make infra-up
make infra-ps
```

等两个容器都 `healthy`。首次启动时 MySQL 会自动执行 `deploy/mysql/init/` 下的脚本，建出 `user` 和 `interaction` 两个库。

**如果数据卷是以前建的**（比如你之前跑过本教程），新加的 `interaction` 库不会自动出现。补执行一次：

```bash
make db-init
```

## 第 2 步：准备配置和密钥

```bash
for svc in user interaction gateway-h5; do
  cp app/$svc/manifest/config/config.yaml.example app/$svc/manifest/config/config.yaml
done
make jwt-keys
```

`make jwt-keys` 打印两行：

```
JWT_PRIVATE_KEY=...   # 只填进 app/user 的 jwt.privateKey
JWT_PUBLIC_KEY=...    # 填进 app/interaction 和 app/gateway-h5 的 jwt.publicKey
```

**私钥只给 user**。其他进程拿到公钥只能验证令牌，签发不了。也可以不改文件，启动时导出同名环境变量。

缺少密钥时进程会直接退出，并报 `jwt.privateKey (or JWT_PRIVATE_KEY) is required`。这是故意的：服务宁可不启动，也不用一个大家都知道的默认密钥。注意每次换密钥，旧令牌都会全部失效。

## 第 3 步：起三个进程（三个终端）

```bash
cd app/user        && go run .   # gRPC :31001
cd app/interaction && go run .   # gRPC :31002
cd app/gateway-h5  && go run .   # HTTP :8199，Swagger 在 http://127.0.0.1:8199/swagger
```

两个 gRPC 服务正常会看到类似：

```
etcd registry enabled at 127.0.0.1:2379
grpc server started listening on [:31001]
```

**如果 etcd 没起**，你会看到 `etcd.address is empty, falling back to the local file registry` 或直接报错。服务仍能启动，但网关会找不到它。

## 第 4 步：走通链路

### 注册

```bash
curl -X POST http://127.0.0.1:8199/frontend/user/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"hugh","password":"correct-horse","sign":"hello"}'
```

```json
{"code":0,"message":"OK","data":{"userId":1}}
```

### 确认真的写进 MySQL

```bash
docker compose exec mysql \
  mysql -ushop -pchange-me user \
  -e 'SELECT id, name, LEFT(password_hash, 16) AS hash_head, LENGTH(password_salt) AS salt_len FROM user_info;'
```

你会看到 `hash_head` 不是明文，`salt_len` 是 16。**如果数据库里能看到你的原始密码，说明哈希没生效 —— 那是 bug。**

### 登录（拿令牌）

```bash
curl -X POST http://127.0.0.1:8199/frontend/user/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"hugh","password":"correct-horse"}'
```

```json
{"code":0,"message":"OK","data":{"tokenType":"Bearer","accessToken":"eyJhbGciOi...","expiresIn":7200,"userId":1,...}}
```

把令牌存进环境变量，后面的请求都带上它：

```bash
TOKEN=$(curl -s -X POST http://127.0.0.1:8199/frontend/user/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"hugh","password":"correct-horse"}' \
  | python3 -c 'import sys,json; print(json.load(sys.stdin)["data"]["accessToken"])')
```

令牌就是你的身份，不要贴到聊天、issue 或日志里。

### 验证鉴权

```bash
# 不带令牌
curl 'http://127.0.0.1:8199/frontend/consignee?page=1&size=10'
# 用旧的 X-User-Id 头冒充
curl 'http://127.0.0.1:8199/frontend/consignee?page=1&size=10' -H 'X-User-Id: 1'
# 篡改令牌最后一个字符
curl 'http://127.0.0.1:8199/frontend/consignee?page=1&size=10' -H "Authorization: Bearer ${TOKEN%?}x"
```

前两个返回 `{"code":16,"message":"missing bearer token"}`，第三个返回 `{"code":16,"message":"invalid access token"}`。**如果任何一个返回了地址列表，那就是严重 bug。**

### 验证隔离

再注册并登录一个用户 `alice`，拿到她的令牌 `TOKEN2` 后：

```bash
curl 'http://127.0.0.1:8199/frontend/consignee?page=1&size=10' -H "Authorization: Bearer $TOKEN2"
```

`total` 应该是 0。**如果这里返回了 hugh 的地址，说明越权了，那是严重 bug。**

```bash

curl -X POST http://127.0.0.1:8199/frontend/praise \
  -H 'Content-Type: application/json' -H "Authorization: Bearer $TOKEN" \

# 再点一次，返回 {"code":6,"message":"resource already exists"}

# 我的点赞列表

# 取消点赞（praiseId 来自上面的列表）

# 收藏和点赞的用法完全一样，把 praise 换成 collection 即可

curl -X POST http://127.0.0.1:8199/frontend/comment \

curl -X POST http://127.0.0.1:8199/frontend/comment \

# 看评论不需要登录
curl 'http://127.0.0.1:8199/frontend/comment?objectType=1&objectId=100'

curl -X DELETE 'http://127.0.0.1:8199/frontend/comment?commentId=1' -H "Authorization: Bearer $TOKEN"
```

自己动手确认这三条规则：

- 用 `TOKEN2` 列点赞，看不到 hugh 的点赞；用 `TOKEN2` 删除 hugh 的点赞或评论，返回 `code:5`（not found），而且数据还在。
- 把回复的 `objectId` 改成 101，返回 `code:3`：回复必须挂在同一个对象的评论下面。
- 不带令牌发表评论，返回 `code:16`。

自己动手确认：

### 下单、取消与超时关单

订单服务需要三把钥匙，配置方法见 [`development/order-service.md`](../development/order-service.md#7-本地运行)。再启动 `app/order`。下面的 `$TOKEN` 是商城用户登录拿到的令牌，`<地址 ID>` 来自前面建的收货地址，`<商品 ID>` 是一件已上架、有库存的商品：

```bash
H=http://127.0.0.1:8199/frontend
# 下单。金额由服务端计算，请求里写什么价格都会被忽略
curl -X POST $H/order -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"requestId":"demo-1","items":[{"goodsId":<商品 ID>,"quantity":2}],"consigneeId":<地址 ID>}'
# → status: PENDING_PAYMENT，expiresAt：15 分钟后。后台商品详情里 reserved 变成 2

# 网络不好、重复点击：同一个 requestId 只会得到同一个订单
curl -X POST $H/order -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"requestId":"demo-1","items":[{"goodsId":<商品 ID>,"quantity":2}],"consigneeId":<地址 ID>}'

# 我的订单、取消（库存立刻还回去）
curl "$H/order" -H "Authorization: Bearer $TOKEN"
curl -X POST $H/order/cancel -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"orderNo":"<订单号>"}'
```

自己动手确认：

- 用另一个用户的令牌查看或取消这个订单，返回 `code:5`。
- 把 `app/order` 配置里的 `order.paymentTimeout` 改成 `30s`，重启，下单后什么都不做，30 秒后再看：订单变成 `CLOSED`，原因是 `PAYMENT_TIMEOUT`，库存回来了。
- 下单数量超过库存：订单直接是 `CLOSED`，原因是 `INSUFFICIENT_STOCK`。
- 对还没付款的订单申请售后（`POST $H/refund`）返回 `code:9`：只有已支付的订单才能申请。付款见下一节。

### 支付

支付要再起一个进程：支付模拟器 `app/paysim`，它冒充外部支付渠道。配置（第四对密钥）见 [`development/payment.md`](../development/payment.md#7-本地运行)。启动 paysim 后，重启 order 和 gateway-h5。

```bash
# 1. 去支付：拿到支付单号和收银台地址
curl -X POST $H/order/pay -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"orderNo":"<订单号>"}'
# → {"paymentId":"P<订单号>","state":"CREATED","payUrl":"http://127.0.0.1:8399/checkout/P<订单号>",...}

# 2. 付款：浏览器打开 payUrl 点"支付"，或者直接
curl -X POST 'http://127.0.0.1:8399/checkout/P<订单号>/pay'

# 3. 一两秒后再看订单：PAID，有 paidAt；后台商品详情里 reserved 少 1、已售多 1
curl "$H/order/detail?orderNo=<订单号>" -H "Authorization: Bearer $TOKEN"
```

背后发生的事：模拟器带签名回调 `POST $H/payment/notify` → 订单服务验签 → **回头去模拟器查询**这笔支付 → 核对金额 → 订单进入 `PAYMENT_CONFIRMING`，提交库存 → `PAID`。看 paysim 的日志能看到 `notify payment ... acknowledged`。

自己动手确认：

- **回调丢了**：新下一单，去支付后用 `.../pay?notify=0` 付款。订单停在 `PENDING_PAYMENT`；再调一次 `/order/pay`，订单立刻变成 `PAID`。
- **付款和取消同时发生**：新下一单，去支付，用 `notify=0` 付款，紧接着取消订单。订单是 `CLOSED`，库存回来了；order 日志里有 `arrived after the order started closing; refund ... scheduled`，几秒后钱自动退回（`orders.tech_refund` 的 `state` 变成 `SUCCEEDED`）。
- **超时**：去支付后什么都不做，等 `paymentTimeout`。订单 `CLOSED`，再去收银台付款返回 409：模拟器那边的支付单已经关了。
- **伪造回调**：`curl -X POST $H/payment/notify -d '{"paymentId":"P<订单号>"}'` 返回 `code:16`，订单不变。
- **回调重试**：停掉 gateway-h5 再付款，paysim 日志里每次失败的间隔翻倍（2s、4s、8s）；重启网关后回调送达，订单变成 `PAID`。
- 付过款的订单可以申请售后了：`POST $H/refund` 返回 `code:0`。

### 事件：准时关单、手工位跟随商品

order、goods、banner 的配置里加上 `rabbitmq.url`（见 [`development/events.md`](../development/events.md#6-本地运行)），然后打开 RabbitMQ 管理界面 <http://127.0.0.1:15672>（`shop` / `change-me`）的 Queues 页。

```bash
# 1. 下一单不付款。order.expiry.delay 队列里多了 1 条消息：它要等到期才会"醒"
curl -X POST $H/order -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"requestId":"demo-mq-1","items":[{"goodsId":<商品 ID>,"quantity":1}],"consigneeId":<地址 ID>}'

# 2. 看它在数据库里的样子：和订单在同一个事务里写进去，几百毫秒后变成 SENT
docker compose exec mysql mysql -ushop -pchange-me orders \
  -e 'SELECT event_id, type, aggregate_id, state, attempts FROM outbox_event ORDER BY id DESC LIMIT 3'
```

到期后（`paymentTimeout` + 1 秒），order 日志出现 `payment time is up; closing (expiry message)`，订单 `CLOSED`。想确认真的是消息关的单，可以把 `recoveryInterval` 临时调到 `60s` 再试一次。

自己动手确认：

- **RabbitMQ 挂了也不丢**：`docker compose stop rabbitmq`，再下一单，下单照常成功；`outbox_event` 里这条是 `PENDING`，`attempts` 在涨。`docker compose start rabbitmq` 后它变成 `SENT`，订单到期照样被关。
- **手工位跟随商品**：在后台把某个手工位上的商品改名，再看 `curl $H/position`，名字跟着变了；把商品下架，这个手工位从前台消失；后台 `/backend/position` 里它还在，`goodsOnShelf` 是 `false`。重新上架，它又回来了。
- **重复只生效一次**：这个不好手工制造，由集成测试证明（同一事件的 10 个并发副本只执行一次）：`GOFRAMESHOP_IT=1 go test ./utility/eventbus/ -run Inbox -v`。

### 链路追踪：在 Jaeger 里看见这一切

`make infra-up` 已经启动了 Collector 和 Jaeger；每个服务的配置里加上 `otel` 一节（见 `config.yaml.example`）后重启。

1. 打开 <http://127.0.0.1:16686>，Service 选 `gateway-h5`，Find Traces，点开一次 `/frontend/order`：网关 → 订单 → 商品（含一次 Redis）、用户 → 写事件的事务 → `publish order.payment_pending`。
2. 付一次款，Service 选 `payment-simulator`，Operation `paysim.notify`：模拟器的回调穿过网关到了订单服务，订单服务又回头查询了模拟器、向商品服务提交了库存。
3. 后台改一次商品名，Service 选 `gateway-admin`：一路能看到 banner 服务消费了 `goods.changed`。
4. 在任意服务的日志里复制一行开头 `{...}` 里的 ID，打开 `http://127.0.0.1:16686/trace/<ID>`。

自己动手确认：

- 点开任意一个 HTTP span 的 Logs，`http.request.headers` 里的 `Authorization` 是 `[REDACTED]`；SQL span 的 `db.statement` 里看不到手机号和地址，只有 `'?'`。
- 等一个订单超时关单，Service `order-service`，Operation `order.recover`：每个被关的订单是单独一条链路。没有订单要处理时，后台任务不产生任何链路。

## 常见报错对照表

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| `code:16` `missing bearer token` | 没带 `Authorization: Bearer` 头 | 先登录，再带上令牌 |
| `code:16` `invalid access token` | 令牌过期、被改动，或 user 服务换过密钥 | 重新登录 |
| 进程启动即退出：`jwt.privateKey ... is required` 或 `jwt.publicKey ... is required` | 没配密钥 | 见第 2 步 |
| `code:16` `invalid access token`，但令牌刚拿到 | 网关或 interaction 配的公钥和 user 的私钥不是同一对 | 重新执行 `make jwt-keys`，三处一起更新 |
| `code:6` `resource already exists` | 重复点赞或重复收藏 | 正常现象，说明已经点过了 |
| interaction、admin 或 file 报 `Internal`，日志显示库不存在 | 数据卷是旧的，没执行过新加的建表脚本 | `make db-init` |
| 后台返回 `code:16` `invalid access token`，但令牌刚拿到 | gateway-admin 或 file 的公钥不是 admin 私钥的那一半，或者误用了商城用户那一对 | 核对管理员密钥对 |
| 后台返回 `code:7` | 普通管理员调用了"创建管理员" | 只有超级管理员可以 |
| 下单总是停在 `RESERVING` | goods 没有配置 `jwtOrder` 公钥，或者和 order 的 `jwtService` 私钥不是一对 | 核对第三对密钥后重启 goods；订单会被后台任务自动推进 |
| 去支付返回 `code:13`，order 日志 `payment provider refused the order service token` | paysim 的 `jwtOrder.publicKey` 和 order 的 `jwtService` 私钥不是一对 | 填和 goods 的 `jwtOrder` 相同的公钥，重启 paysim |
| 去支付返回 `code:14` | paysim 没有启动，或者没有注册到 etcd | 启动 `app/paysim` |
| 付了款订单还是 `PENDING_PAYMENT`，paysim 日志 `merchant refused with code 16` | order 的 `paysim.publicKey` 和 paysim 的 `notify.privateKey` 不是一对 | 核对第四对密钥后重启 order；模拟器会继续重试，也可以再调一次 `/order/pay` |
| paysim 日志 `connection refused` | gateway-h5 没起，或 `notify.url` 写错 | 启动网关；模拟器会按退避继续重试 |
| order / goods / banner 启动报 `rabbitmq.url (or RABBITMQ_URL) is required` | 配置里没有 `rabbitmq.url` | 照 `config.yaml.example` 补上 |
| 日志 `consumer ...: dial tcp 127.0.0.1:5672: connect: connection refused` | RabbitMQ 没起 | `make infra-up`；消费者会自己重连 |
| 日志 `tracing is off: otel.endpoint is not set` | 配置里没有 `otel` 一节 | 照 `config.yaml.example` 补上；不加也能运行，只是 Jaeger 里看不到这个服务 |
| Jaeger 里找不到某个服务 | 服务没配 `otel.endpoint`，或 Collector 没起 | `docker compose ps otel-collector`；看服务启动日志里有没有 `tracing on` |
| 日志 `outbox event ... no queue bound for the routing key` | 新加的事件类型没在 `utility/rabbitmq/topology.go` 里绑定队列 | 加上绑定后重启；事件一直留在 outbox 里等着，不会丢 |
| order 启动失败：`jwtUser.publicKey ... is required` | order 的三把钥匙没配齐 | 见 order-service.md 第 7 节 |
| 下单返回 `code:9` `some goods are unavailable` | 商品已下架、已删除或不存在 | 先在后台上架 |
| search 启动失败：`elasticsearch is not reachable` | ES 没起，或者刚启动还没就绪 | `make infra-ps`，等 elasticsearch 变成 healthy |
| search 启动失败，报 binlog 或权限错误 | 没执行 007，缺少 `search_sync` 账号 | `make db-init` |
| 调整库存返回 `code:9` `not enough available stock` | 出库数量超过了可用库存 | 先查商品详情里的 `stock` |
| 后台删除分类返回 `code:9` | 分类下还有子分类或商品 | 先删掉子分类和商品 |
| 建商品返回 `code:3` | 分类链不对，比如二级分类不属于所填的一级分类 | 用 `/backend/category/all` 核对 `parentId` |
| goods 日志里有 `cache read failed, falling back to MySQL` | Redis 没起或密码不对 | `make infra-ps`；核对 goods 配置里的 `redis.default.pass` |
| 上传返回 `image upload failed` | 存储后端出错，比如七牛凭据或域名不对 | 看 gateway-admin 日志里的 `image upload to ... failed` |
| `InvalidArgument` | 字段为空或超长 | 看响应 message |
| `Unknown` / 连接被拒 | user 服务没起，或 etcd 里没有它 | `etcdctl get --from-key " " --keys-only` 看看有没有 `/service/user` |
| `Internal: internal error` | 数据库连不上 | `make infra-ps`，检查 `config.yaml` 里的账号密码 |
| 编译报 `table.SetHeader undefined` | gf 被降级到 v2.9.0 | 见下一节 |

## 一个真实的坑：`go mod tidy` 会悄悄降级 GoFrame

本轮开发时踩到过：跑完 `go mod tidy` 之后

```
github.com/gogf/gf/v2@v2.9.0/net/ghttp/ghttp_server.go:300: table.SetHeader undefined
```

原因是 `tidy` 把 GoFrame 从锁定的 **v2.10.2** 降到了 v2.9.0，而 v2.9.0 的 `ghttp` 用的是旧版 `tablewriter` 的 API，和当前 `tablewriter v1.1.0` 不兼容。

修复：显式把版本拉回基线。

```bash
go get github.com/gogf/gf/v2@v2.10.2 \
       github.com/gogf/gf/contrib/rpc/grpcx/v2@v2.10.2 \
       github.com/gogf/gf/contrib/drivers/mysql/v2@v2.10.2 \
       github.com/gogf/gf/contrib/registry/etcd/v2@v2.10.2
go mod tidy
go list -m github.com/gogf/gf/v2   # 确认输出 v2.10.2
```

**记住：`go mod tidy` 会为了补全缺失依赖去拉最新版本，这可能越过仓库锁定的版本。跑完之后一定要 `go list -m` 复核。**
