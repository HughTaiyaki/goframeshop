# 02 · 代码分四层，每层该干什么

> 四层不是形式主义。每一层存在的理由，都是"**让某一类变化只影响一处**"。

## 分层图

```
Controller     传输层：HTTP/gRPC 进来，HTTP/gRPC 出去
   │           只做三件事：取身份 / 调用 service / 转换结构体
   ▼
Service        接口：定义"能做什么"（internal/service）
   │
   ▼
Logic          实现：业务规则在这里（internal/logic）
   │           默认地址互斥、密码哈希、越权判断
   ▼
Repository     接口 + 实现：SQL 语义（internal/service + internal/repository）
   │           软删除、分页、事务
   ▼
DAO            生成代码：表名 / 字段名常量（internal/dao）
```

## 每层的准入规则

| 层 | 允许 | 禁止 |
| --- | --- | --- |
| Controller | 解析请求、取身份、调 service、转结构体、映射错误码 | 写 SQL、写业务规则、直接操作 DAO |
| service（接口） | 只定义类型和错误 | 任何实现代码 |
| logic（实现） | 业务规则、调 repository | 知道 HTTP 或 gRPC 的存在 |
| repository | 拼 SQL、开事务 | 决定业务含义 |
| DAO | 由 `gf gen dao` 生成 | **手改**（标记 `DO NOT EDIT`） |

判断一句话：**如果这段代码换个协议（HTTP 换 gRPC）还要重写，它就不该在 Controller 之上；如果它换个数据库还要重写，它就不该在 Repository 之下。**

## 为什么要定义接口（service / repository 都是接口）

看 `internal/service/repository.go`：

```go
type ConsigneeRepository interface {
    Create(ctx context.Context, c *entity.ConsigneeInfo) (uint64, error)
    ListByUser(ctx context.Context, userID uint64, page, size int) ([]*entity.ConsigneeInfo, error)
    ...
}
```

logic 层只认这个接口，不认 MySQL。**回报在测试里直接兑现**：

```go
// internal/logic/consignee/consignee_test.go
svc := New(newFakeConsigneeRepo())   // 内存实现，不需要 Docker
```

所以 `go test ./...` 在没有 MySQL 的机器上也能跑通全部业务规则。如果 logic 直接 `import dao`，这些测试就一个都写不了。

这也解释了为什么 `logic` 的构造函数是 `New(repo)` 而不是在内部 new 一个 repo：**依赖注入是为了让"用什么实现"成为一个可以在测试里换掉的决定。**

## `internal/logic/logic.go` 这一层是干什么的

```go
func Consignee() service.IConsignee {
    return consignee.New(repository.NewConsignee())
}
```

只有这一个文件知道「用的是 MySQL 版 repository」。想换成带缓存的实现、想在测试里换成 fake，都只需要改这里。

## 五个常见错误（教程里踩过，本仓库明确禁止）

### 1. 把请求对象直接塞进 DAO

```go
// ❌ 教程写法
dao.ConsigneeInfo.Ctx(ctx).InsertAndGetId(req)
```

`req` 是 gRPC 请求体，**客户端能控制它的每一个字段**。今天它没有 `user_id` 字段，明天有人加了一个，所有旧客户端瞬间就能伪造身份。正确做法是在 logic 里显式构造 entity：

```go
// ✅ 本仓库写法
record := &entity.ConsigneeInfo{
    UserId: userID,        // 来自身份，不是来自请求
    Name:   in.Name,
    ...
}
```

### 2. 数据库出错时返回空结果

```go
// ❌ 教程写法
total, err := dao.ConsigneeInfo.Ctx(ctx).Count()
if err != nil {
    return &v1.Response{Data: response}, nil   // 错误被吞了
}
```

调用方拿到「0 条地址」和 nil error —— 它无法区分"你真的没有地址"和"数据库挂了"。对后面的诊断 Agent 来说，这是**伪造证据**。本仓库一律 `return nil, err`。

### 3. 把 `pbentity` 直接当响应

`gf gen pbentity` 生成的是**数据库表的镜像**，里面带 `password_hash`、`secret_answer_hash`、`deleted_at`。直接把它丢给客户端，等于把数据库结构当 API 契约 —— 你以后改一次表结构，API 就 breaking change 一次。

所以协议里单独定义了 `Consignee` 消息，Controller 负责转换。

### 4. 忽略 Delete 的错误

```go
// ❌ 教程写法
_, err = dao.ConsigneeInfo.Ctx(ctx).Where("id", req.Id).Delete()
return &v1.DeleteRes{}, nil    // err 被丢掉
```

### 5. 用 MD5 存密码

MD5 太快了 —— 一张显卡每秒能算几百亿次，撞库几乎是免费的。本仓库用 **Argon2id**：每次计算都要 64 MiB 内存，把"批量猜测"的成本抬高几个数量级。盐是随机生成的，写进 `password_salt` 列。

## 一个文件一个文件读

想最快搞懂业务，按这个顺序读：

1. `app/user/internal/service/consignee.go` —— 能做什么
2. `app/user/internal/logic/consignee/consignee.go` —— 规则是什么
3. `app/user/internal/repository/consignee.go` —— 怎么落库
4. `app/user/internal/controller/consignee/consignee.go` —— 怎么接进来
