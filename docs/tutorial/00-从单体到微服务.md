# 00 · 从单体到微服务：换掉了什么

> 目标读者：只写过单体项目的人。读完后你应该能回答：**为什么一个「新增收货地址」要拆成两个进程、三层代码。**

## 单体里，一次新增地址是什么样

```go
// 单体：全部在一个进程里
func CreateAddress(c *gin.Context) {
    var req AddressReq
    c.ShouldBindJSON(&req)          // 1. 解析 HTTP
    if err := validate(req); ...    // 2. 校验
    db.Exec("INSERT INTO ...")      // 3. 写库
    c.JSON(200, "ok")               // 4. 回响应
}
```

四件事发生在**同一个进程、同一个内存、同一个事务**里。最关键的一点：**第 3 步不会失败得很奇怪** —— 要么成功，要么返回一个你能 catch 的错误。没有"超时"，没有"半途网络断了"。

## 微服务把它换成什么

微服务把「进程内的函数调用」换成「跨进程的网络调用」：

| 单体 | 微服务 |
| --- | --- |
| `service.CreateAddress(req)` | `client.CreateConsignee(ctx, req)` |
| 传的是指针 | 传的是序列化后的字节（Protobuf） |
| 失败 = panic / error | 失败 = 错误 **或** 超时 **或** 连接被拒 **或** 目标不存在 |
| 编译期就知道方法存在 | 靠**协议文件**（`.proto`）约定，两端各自生成代码 |
| 一台机器一个进程 | 多个进程，可能在不同机器上 |

**一句话记住这个差别**：函数调用只有"成功/失败"两种结果；RPC 有第三种结果 —— **不知道**，因为你没收到回复。这就是为什么微服务代码里到处是 `context.WithTimeout`。

## 为什么要付这个代价

不是所有项目都该拆。值得拆的理由通常只有这几个：

1. **独立部署**：改收货地址不用重新发布商品服务。
2. **独立扩缩**：下单流量是查资料的 100 倍，只给订单服务加副本。
3. **故障隔离**：支付服务挂了，用户还能浏览商品。
4. **团队边界**：两个团队不必挤在同一个代码库里改同一批文件。

对应到本项目，真正想做的实验是第 5 条 —— `AGENTS.md` 里写得明白：先造一个**能产生可信日志、指标、链路**的分布式系统，然后才去写「日志诊断 Agent」。微服务不是为了赶时髦，是为了有东西可诊断。

## 代价清单（每一条都会在这个仓库里遇到）

| 代价 | 本项目怎么应对 |
| --- | --- |
| 调用方不知道服务在哪 | etcd 服务发现（见 01） |
| 网络调用可能永远不返回 | 客户端超时拦截器（`utility.GrpcClientTimeout`） |
| 两端数据结构要一致 | Protobuf 协议文件 + `gf gen pb` |
| 失败要能区分类型 | gRPC 状态码 + `controller.StatusError` |
| 不能跨库事务 | 默认地址切换放进单个服务的单库事务 |
| 排错变难 | 结构化日志 + 后续接 OpenTelemetry |

## 这个项目现在有几个进程

```
gateway-h5     HTTP :8199   面向浏览器，自己不碰数据库
user           gRPC :31001  用户资料 + 收货地址，独占 user 库，唯一能签发令牌
interaction    gRPC :31002  点赞 + 收藏 + 评论，独占 interaction 库

gateway-admin  HTTP :8299   后台入口，把图片写进七牛或本地目录
admin          gRPC :31003  管理员身份，独占 admin 库，唯一能签发管理员令牌
file           gRPC :31004  文件元数据，独占 file 库
goods          gRPC :31005  商品 + 图片 + 分类 + 库存账本，独占 goods 库，读走 Redis 缓存
search         gRPC :31006  商品搜索，读 Elasticsearch；通过 binlog 跟随 goods 库
order          gRPC :31007  下单、支付、关单、售后，独占 orders 库；用自己的服务身份调用库存和支付模拟器
banner         gRPC :31008  首页轮播图和手工位，独占 banner 库

paysim         gRPC :31009  支付模拟器：假装自己是微信、支付宝这类"别人的系统"，独占 paysim 库
               HTTP :8399   收银台页面，付款人在这里点"支付"

MySQL 8.4.11   :3306
etcd 3.6.1     :2379        只做服务发现，不存业务数据
Redis 7.4.2    :6379        只做缓存，清空也不丢数据
Elasticsearch  :9200        搜索索引，随时可以从 MySQL 重建
RabbitMQ       :5672        服务之间的事件（"商品改名了""订单该关了"），先记在各自的库里再投递
OTel Collector :4317        收集每个服务的链路数据，转给 Jaeger
Jaeger         :16686       链路追踪界面：一次请求经过了哪些服务、每一步花了多久
```

`user` 和 `interaction` 用的是同一个 MySQL 实例里的**两个库**，并且互相不读对方的库。interaction 想知道"这是谁"，靠的是令牌，不是去查 user 库。

`paysim` 有点特别：它不是商城的一部分，而是**冒充外部系统**。订单服务不能查它的库，只能调它的接口，而且要准备好它超时、重复回调、回调丢失。这样写出来的代码，换成真的支付渠道时规则不用变。

注意 `gateway-h5` **没有数据库**。这本身就是微服务和单体最直观的区别之一：网关只是一个翻译器，把 HTTP/JSON 翻译成 gRPC。
